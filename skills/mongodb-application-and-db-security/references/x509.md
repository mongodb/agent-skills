# x.509 client authentication

x.509 client authentication is mutual TLS: the client proves its identity with a certificate,
and MongoDB maps the certificate's subject to a user in `$external`. This file covers client
authentication. Member-to-member x.509 (`security.clusterAuthMode: x509`) is a separate setup.

For Atlas (Atlas-managed certificates or your own CA), use `atlas.md`. The steps below are
self-managed.

## Certificate requirements

The client certificate must meet all of these:

- Issued by the same CA that issued the server certificates.
- Contains `keyUsage = digitalSignature` and `extendedKeyUsage = clientAuth`.
- At least one of **O, OU, or DC** differs from the member certificates
  (`net.tls.clusterFile` and `net.tls.certificateKeyFile`). This is a security requirement, not
  just a formatting rule. If a client certificate's O, OU, and DC exactly match the member
  certificate, MongoDB accepts the connection as a cluster member **with full permissions** and
  only logs a warning. If the deployment sets `tlsX509ClusterAuthDNOverride`, the client
  subject must not match that value either. Whether the server actually applies this depends on
  its cluster-authentication setup, so keep client attributes distinct on every deployment.
  Never disable the `enforceUserClusterSeparation` parameter: turning it off disables the
  O/OU/DC check.
- Each client certificate maps to exactly one MongoDB user.

## Server configuration

```yaml
net:
  tls:
    mode: requireTLS
    certificateKeyFile: <SERVER_PEM_PATH>
    CAFile: <CA_PEM_PATH>
security:
  authorization: enabled
```

A CA source is mandatory: `net.tls.CAFile`, or the `tlsUseSystemCA` parameter. Don't set
`net.tls.allowInvalidCertificates`. With it set, an invalid certificate can still open a TLS
connection, but it isn't enough to authenticate, and it removes the protection TLS gives.

**Pre-change check: the server must accept MONGODB-X509.** It's in the default list
(`MONGODB-X509,SCRAM-SHA-1,SCRAM-SHA-256`), but operators sometimes narrow it. The user checks
the effective value on every `mongod` and `mongos`:

```javascript
db.adminCommand({ getParameter: 1, authenticationMechanisms: 1 })
```

If the list is customized and lacks `MONGODB-X509`, add it, and keep every mechanism existing
users still rely on (for example `SCRAM-SHA-256` for SCRAM users, `PLAIN` for LDAP users):

```yaml
setParameter:
  authenticationMechanisms: "MONGODB-X509,SCRAM-SHA-256"
```

This parameter is startup-only, so the change needs a rolling restart.

- **Post-change check:** `getParameter` shows the new list, and an existing SCRAM user still
  logs in.
- **Rollback criterion:** if existing users can't authenticate after a member restarts, restore
  that member's previous `setParameter` value and restart it before continuing.

**Conditional: clients that don't present a certificate.** With `net.tls.CAFile` set, every
client must present a valid certificate by default. That includes SCRAM clients. If existing
applications authenticate with SCRAM and have no client certificate, they'll fail the TLS
handshake. For that mixed case, add:

```yaml
net:
  tls:
    allowConnectionsWithoutCertificates: true
```

- **What it changes:** only the TLS handshake. Clients without a certificate still connect over
  encrypted TLS. Certificates that are presented are still validated, and invalid ones are
  rejected.
- **What it doesn't change:** database authentication. With `security.authorization: enabled`,
  those clients still have to authenticate, for example with SCRAM, before they can do anything.
- **Don't set it if every client uses x.509.** Requiring a certificate from every client is the
  stricter posture.

## Create the user

1. Print only the subject, in RFC 2253 format. `-noout` suppresses the certificate body:

   ```bash
   openssl x509 -in <CLIENT_PEM_PATH> -inform PEM -noout -subject -nameopt RFC2253
   ```

   Sample output:

   ```text
   subject=CN=reporting-app,OU=Apps,O=Example,L=City,ST=State,C=US
   ```

2. Take only the DN after `subject=`. Here that's
   `CN=reporting-app,OU=Apps,O=Example,L=City,ST=State,C=US`. Some OpenSSL versions print
   `subject= ` with a space after the `=`; drop that too. Before creating the user, check that:
   - the value doesn't start with `subject=`;
   - there are no leading or trailing spaces;
   - the RDNs are comma-separated in the order shown, with no spaces after the commas;
   - any escaped characters (such as `\,`) are kept exactly as printed.

3. Create the user in `$external` with that DN:

   ```javascript
   db.getSiblingDB("$external").runCommand({
     // example value: "CN=reporting-app,OU=Apps,O=Example,L=City,ST=State,C=US"
     createUser: "<CERT_SUBJECT_DN>",
     roles: [ { role: "<CUSTOM_ROLE>", db: "<ROLE_DB>" } ],
     writeConcern: { w: "majority", wtimeout: 5000 }
   })
   ```

   There's no password. The certificate is the credential.

## Connect

mongosh:

```bash
mongosh "mongodb://<HOST>:27017/" --tls \
  --tlsCertificateKeyFile <CLIENT_PEM_PATH> \
  --tlsCAFile <CA_PEM_PATH> \
  --authenticationDatabase '$external' \
  --authenticationMechanism MONGODB-X509
```

Connection string options: `tls=true`, `tlsCertificateKeyFile=<PATH>`, `tlsCAFile=<PATH>`,
`authMechanism=MONGODB-X509`.

- No username is needed. The server takes it from the certificate.
- Drivers use `$external` for MONGODB-X509. If you set `authSource`, it must be `$external`
  (`%24external` in a URI).
- In a URI, percent-encode file paths with `encodeURIComponent`.
- If the private key is encrypted, pass the password with `tlsCertificateKeyFilePassword`,
  read from a secret store. Never put it inline.

## Operating it

- Make the client PEM (certificate plus private key) readable only by the service account that
  runs the application, for example `chmod 600`. Never commit it to source control or bake it
  into images.
- Track expiry dates and alert well before they arrive.
- **Routine replacement (the old certificate isn't compromised):**
  - **Same subject:** no database change is needed. Both the old and the new certificate
    authenticate as the same user until the old one expires. To retire the old one before
    expiry:
    1. Remove it, and its private key, from every client host.
    2. Confirm no connections still present it.
    3. Revoke it at the CA if your policy requires early retirement.
  - **Different subject:**
    1. Create the new `$external` user.
    2. Deploy the new certificate.
    3. Drop the old user once nothing connects with the old certificate. `dropUser` can't be
       undone.
    4. Post-change check: a new connection using the old certificate fails to authenticate.
- **Compromised certificate:** follow the incident procedure below. Replacing the certificate
  isn't enough: a compromised certificate with the same subject keeps authenticating until it
  expires or every server rejects it as revoked.

## Incident procedure: cutting off a compromised certificate

Two separate problems: stopping **new** authenticated connections with the certificate, and
dealing with connections that are **already** authenticated. The user runs every check below.
Don't report the certificate as cut off until all of them pass.

### A. Stop new connections

Choose one path, or use both:

**Path 1: revocation.**

1. **Find where the certificate publishes revocation information:**

   ```bash
   openssl x509 -in <COMPROMISED_CERT_PEM> -noout -ext authorityInfoAccess,crlDistributionPoints
   ```

   - An OCSP URL appears under Authority Information Access.
   - A CRL location appears under CRL Distribution Points.
   - If the output says `No extensions in certificate` or shows neither, OCSP can't be used for
     this certificate. Use a CRL file or Path 2.

2. **Revoke the certificate at the CA.**

3. **Confirm every `mongod` and `mongos` will check revocation:**
   - **OCSP:** `ocspEnabled` must be `true`. That's the default on Linux and macOS, and it's
     startup-only. Check it with `db.adminCommand({ getParameter: 1, ocspEnabled: 1 })`. Each
     server host must be able to reach the OCSP responder. From each host, run:

     ```bash
     openssl ocsp -issuer <ISSUING_CA_PEM> -cert <COMPROMISED_CERT_PEM> -url <OCSP_URL> -resp_text
     ```

     It must report the certificate as `revoked`.
   - **CRL:** `net.tls.CRLFile` must point at a CRL that lists the certificate. It isn't
     available on macOS. A server only uses an updated CRL after it reloads the file, so confirm
     how your version reloads it (restart, or certificate rotation) and do that on every member
     and router. Check the effective setting with `db.adminCommand({ getCmdLineOpts: 1 })` under
     `parsed.net.tls.CRLFile`.

**Path 2: remove the identity.**

1. If you need to keep the client running, issue a certificate with a **new subject**, create
   that `$external` user, and move the client over.
2. Drop the old `$external` user.

This works whatever the revocation status, because no user matches the old subject.

**Required check for either path:** from a host that has the compromised certificate, open a
**new** connection to **each** `mongod` and `mongos` directly. For example:

```bash
mongosh "mongodb://<HOST>:<PORT>/?directConnection=true" --tls \
  --tlsCertificateKeyFile <COMPROMISED_CERT_PEM> --tlsCAFile <CA_PEM_PATH> \
  --authenticationDatabase '$external' --authenticationMechanism MONGODB-X509 \
  --eval 'db.runCommand({ connectionStatus: 1 })'
```

Every attempt must fail at the TLS handshake or at authentication. A single success means that
server still accepts the certificate.

### B. Deal with existing connections

MongoDB's documentation doesn't say that revoking a certificate or dropping a user closes
connections that already authenticated. Treat them as still open until shown otherwise.

1. **Find them.** As an admin with `inprog` privileges, on each `mongod` and `mongos`:

   ```javascript
   db.getSiblingDB("admin").aggregate([
     { $currentOp: { allUsers: true, idleConnections: true } },
     { $match: { "effectiveUsers.user": "<CERT_SUBJECT_DN>" } }
   ])
   ```

2. **End the user's sessions and operations.**

   ```javascript
   db.getSiblingDB("admin").runCommand({
     killAllSessionsByPattern: [ { users: [ { user: "<CERT_SUBJECT_DN>", db: "$external" } ] } ]
   })
   ```

   This needs `killAnySession` and `impersonate`. It ends sessions and their in-progress
   operations and cursors, but the connections themselves can stay open.

3. **Close the connections.** Restart or redeploy the client that held the certificate. If you
   can't reach it, do a rolling restart of the members and routers it connected to.

4. **Allow for cached authorization data.** On `mongos`, the user cache is refreshed on an
   interval (30 seconds by default). Rerun the new-connection check in part A after that
   interval has passed.

5. **Post-incident check:** the `$currentOp` query returns nothing on every server, and the
   part A check still fails everywhere.

On Atlas, certificates can't be revoked. Delete the database user to stop new connections (see
`atlas.md`), then handle existing connections as above, as far as Atlas permissions allow.

## Verify

```javascript
db.runCommand({ connectionStatus: 1 })
// authInfo.authenticatedUsers: [ { user: "<CERT_SUBJECT_DN>", db: "$external" } ]
```

Then run one operation the role allows and one it doesn't (the second must fail with
`Unauthorized`, code 13).

## Pitfalls

- Subject stored with different spacing or RDN order than the RFC 2253 output. Authentication
  fails.
- Client certificate O/OU/DC identical to the member certificate. MongoDB grants the client full
  cluster permissions and records only a warning in the log.
- Using `tlsAllowInvalidCertificates` or `tlsInsecure` to get past a certificate error instead
  of fixing the CA chain or hostname.
- Server hostname not in the server certificate's SAN, so client hostname verification fails.
  Fix the certificate; don't turn off verification.
